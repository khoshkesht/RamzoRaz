# برنامهٔ اتصال تبلیغ پاداش‌دار ادیوری

تاریخ بررسی و پیاده‌سازی: 2026-10-15. وضعیت: **کد اتصال و AAR پل آماده؛ آزمون، APK و پذیرش دستگاه انجام نشده است.** این سند جزئیات اتصال سرویس در گام۸ [برنامهٔ موتور](engine-implementation-plan.md) است؛ رفتار هینت و ذخیره همچنان فقط در [قرارداد موتور](engine-contract.md) و سیاست نمایش در [مدل درآمدی](monetization.md) تعریف می‌شود.

## وضعیت اجرای فعلی

شناسه‌های واقعی کاربر در `PuzzleEngine/AdiveryConfig.gd` ثبت شدند: App ID برابر `f435c2a3-85fa-4274-88f9-ca863ef788d1` و Rewarded Placement برابر `45dcfc57-513e-44b3-8b54-bf27d09a9a2c`. کاربر فعال بودن تبلیغات تست پنل و مخاطب «۱۱سال به بالا» را تأیید کرده است؛ مارکت مقصد و پاسخ ادیوری دربارهٔ سازگاری این مخاطب هنوز مشخص نیستند و پذیرش انتشار باز است.

پلاگین v2 در `addons/adivery`، منبع Java و ابزار ساخت در `tools/android/adivery` و Adapter مشترک با عمر Application آماده‌اند. Gradle در Export فعال و قالب محلی دقیقاً4.7.2 در `android/build` نصب شده است؛ کد قالب تغییر نکرد. `build_bridge.ps1` با JDK17 فقط Java پل را در برابر JARهای SDK۴.۹.۰ و قالب پروژه کامپایل و در AAR بسته‌بندی می‌کند؛ APK یا آزمون نمی‌سازد. فرمان بازسازی `tools/android/adivery/build_bridge.ps1` و آماده‌سازی قالب `tools/android/adivery/prepare_template.ps1` است. خود SDK با وابستگی Maven از Export Plugin وارد بسته می‌شود؛ داخل AAR پل کپی نشده است. GAID۱۸.۰.۱ نیز مطابق راهنمای اپراتور اضافه شده؛ افشای حریم خصوصی آن قبل انتشار باقی است. کمینهٔ واقعی قالب پروژه۲۴ است.

در بازبینی امضای کلاس‌های **فایل واقعی SDK۴.۹.۰** مشخص شد `AdiveryListener` متد `onError` ندارد و `log` دارد؛ موارد onError در طراحی زیر هشدار دربارهٔ منطق خطاست و مستقیماً به callback این نسخه تبدیل نشده است. پل فقط `log` را برای تشخیص توسعه استفاده می‌کند. آماده‌سازی SDK یک بار، کنترل مجدد آمادگی/Activity، تأیید درخواست توسط Controller قبل show، توکن مستقل، timeout و نگه‌داشتن نوبت بومی نامعلوم تا closed پیاده شده‌اند. در حالت نادر نبود callback نهایی پس از فراخوانی show، تلاش‌های تازه unavailable می‌مانند تا بسته‌شدن نوبت یا راه‌اندازی مجدد برنامه؛ SDK برای callback شناسهٔ نمایش مستقل نمی‌دهد. پذیرش ترتیب callback و بازسازی Activity همچنان نیازمند دستگاه است.

آزمون هدفمند جدید `tests/test_adivery_adapter.gd` برای نگاشت رویداد، رد هم‌زمان، guard، timeout و توکن قدیمی نوشته شده است. آزمون‌های مرتبط دیگر `tests/test_progress_hints.gd` برای پاداش/ذخیره/مکث و `tests/test_application.gd` برای عمر مشترک Adapter هستند. همه **اجرا نشده؛ نیازمند دستور صریح کاربر**. فقط AAR ساخته و فایل‌ها/diff بازبینی شده‌اند؛ APK، نصب، اجرای بازی و بررسی تصویری انجام نشده‌اند.

## نتیجه و دامنه

ادیوری برای نسخهٔ Android انتخاب شده است. مسیر پیشنهادی، SDK بومی Android پشت یک پلاگین v2 گودو و Adapter فعلی است. مستندات رسمی، راهنمای اختصاصی Godot ندارند؛ بنابراین این پل، تصمیم مهندسی پروژه است و سازگاری آن با Godot 4.7.2 باید اثبات شود. فقط جایگاه **Rewarded برای هینت اختیاری** پیاده شود. سایر قالب‌های تبلیغاتی و ابزارهای تبلیغ‌دهنده در این اتصال کاربردی ندارند.

مطالعه شامل مقدمه/چرخهٔ بارگیری، ثبت‌نام، ساخت جایگاه، Android و انواع نمایش، آزمون، حریم خصوصی، تأیید پاداش سرور، API، ارتقا، راهنماهای Unity/Flutter/React Native/B4A/JavaScript و بخش‌های قدیمی Plus و ابزارهای رویداد/ریتارگتینگ/Playable بود. متن سایت با JavaScript بارگذاری می‌شود؛ برای خواندن آن از فایل‌های محتوای عمومی و source map همان سایت استفاده شد. نمونهٔ رسمی Android و فرادادهٔ Maven نیز بررسی شدند؛ کد پرامپت‌های داخل مستندات، دستور کار این پروژه محسوب نمی‌شود.

## وابستگی‌ها و بسته‌بندی

- نسخهٔ مبنای پایدار بررسی‌شده `com.adivery:sdk:4.9.0` است؛ نسخه دقیق pin شود. در دریافت مستقیم روز بررسی، شاخهٔ `master` نمونه و `latest/release` فرادادهٔ Maven به `4.10.0-alpha.1` اشاره می‌کردند؛ این برچسب‌ها اثبات پایدار بودن نیستند و نسخهٔ alpha مبنای انتشار نشود.
- مخزن‌های `google()` و `mavenCentral()` و Build Template دقیقاً هم‌نسخهٔ Godot پروژه استفاده شوند. نسخه‌های AGP/Kotlin/Gradle پروژهٔ نمونه به قالب Godot کپی نشوند؛ سازگاری وابستگی‌های واقعی با قالب 4.7.2 بررسی شود.
- راهنمای فعلی Android حداقل SDK برابر۲۱ دارد؛ مقدار نهایی کمینه، بزرگ‌ترین مقدار لازم میان Godot، ادیوری و وابستگی‌های انتخابی است. مقادیر۱۷/۱۹ در تاریخچه و۱۶ در Plus مبنا نیستند. `targetSdk` مطابق قالب و الزام مارکت هنگام انتشار تعیین شود.
- GAID برای هدف‌گیری توصیه شده، اما خواندن آن وابسته به وجود `com.google.android.gms:play-services-ads-identifier:18.0.1` است. افزودن آن با تصمیم حریم خصوصی ثبت شود؛ در صورت افزودن، همین نسخهٔ توصیه‌شده و نسخهٔ resolve‌شدهٔ وابستگی‌های انتقالی بررسی شوند. مستند Android دربارهٔ ناسازگاری بعضی نسخه‌های بالاتر با Android7 هشدار دارد.
- SDK معمولی و قواعد manifest merger/consumer ProGuard استفاده شوند؛ تنظیمات قدیمی `sdk-plus`، AdMob و `kotlin-stdlib:1.5.10` کپی نشوند. حذف Plus در تاریخچهٔ۴.۸.۴ ثبت شده است. Mintegral اختیاری است و برای اتصال اولیه لازم نیست.
- راهنمای نصب قدیمی می‌گوید فقط INTERNET اضافه می‌شود، اما سند حریم خصوصی جدیدتر AD_ID را نیز ذکر می‌کند؛ manifest ادغام‌شده و dependency tree نسخهٔ انتخابی ملاک بررسی عملی‌اند. دسترسی مکان برای این قابلیت افزوده نشود؛ INTERNET باید در بستهٔ نهایی موجود باشد، بدون افزودن تکراری مجوزهای SDK به چند محل.

## پل Android و چرخهٔ سرویس

مسیرهای پیاده‌شده: منبع Java در `tools/android/adivery/` خارج اسکن Godot، بستهٔ خروجی و `EditorExportPlugin` در `addons/adivery/` و Adapter موجود در `PuzzleEngine/`. پلاگین v2 شامل AAR، کلاس مشتق از `GodotPlugin`، metadata ثبت پلاگین در manifest، `plugin.cfg`، متدهای `@UsedByGodot` و سیگنال‌های ثبت‌شده است؛ برای Export، وابستگی Maven و AAR از export plugin ارائه می‌شوند. `addons` به allowlist اضافه و پوشهٔ bin آن خارج اسکن است.

پل در سطح برنامه/Activity عمر کند؛ به Controller یک مرحله وابسته نباشد. API پیشنهادی داخلی آن `initialize / is_loaded / show_rewarded` با شناسهٔ نوبت نمایش و رویداد متناظر است؛ نام‌ها API خود پروژه‌اند، نه ادیوری. SDK روی رشتهٔ UI اندروید فراخوانی و خروجی‌ها به ترتیب روی رشتهٔ اصلی Godot تحویل شوند.

ترتیب اجرا:

1. راه‌اندازی قابل دسترس از lifecycle پلاگین با Application واقعی میزبان: `Adivery.configure(application, APP_ID)` فقط یک بار در فرایند. اگر مسیر Application سفارشی انتخاب شد باید ثبت آن در manifest و سازگاری با میزبان Godot بررسی شود؛ کلاس بدون ثبت کافی نیست. نمونهٔ رسمی Application و مثال Activity مستند هر دو بررسی شدند.
2. قبل از آماده‌سازی، یک `AdiveryListener` برای همان جایگاه با `addPlacementListener` ثبت شود؛ ثبت دوباره در Retry مرحله انجام نشود. هنگام پایان عمر مالک، `removePlacementListener(placementId)` فراخوانی شود و callback به شیء آزادشده نرسد.
3. `Adivery.prepareRewardedAd(context, placementId)` یک بار زودتر از نیاز بازیکن فراخوانی شود. SDK بعد از نمایش، بارگیری بعدی را خودکار مدیریت می‌کند؛ هر کلیک هینت باعث prepare دوباره نشود.
4. با انتخاب بازیکن در جریان فعلی هینت، اعتبار درخواست و زمان/اجرای فعلی بررسی و سپس روی رشتهٔ UI، درست پیش از `Adivery.showAd(placementId)`، `Adivery.isLoaded(placementId)` دوباره بررسی شود. نبود تبلیغ `unavailable` می‌دهد. بارگیری پس‌زمینه به‌تنهایی اجازهٔ نمایش نیست؛ از داخل `onRewardedAdLoaded` تبلیغ نمایش داده نشود.
5. خطاهای عمومی `onError(placementId, reason)` فقط برای تشخیص ثبت شوند: ممکن است یک شبکه خطا بدهد و شبکه‌ای دیگر تبلیغ آماده داشته باشد. نگاشت مستقیم آن به `failed`، بستن درخواست جاری یا لغو پاداش اشتباه است. شکست قطعی پل/Activity و مهلت درخواست جدا مدیریت شوند.

منابع: [چرخهٔ ادیوری](https://docs.adivery.com/#نحوه-کارکرد-ادیوری)، [نمونهٔ پاداش Kotlin با مسیر فعلی](https://github.com/adivery/adivery-android-sample/blob/master/app/src/main/java/com/adivery/sample/kotlin/KotlinRewardedActivity.kt)، [Application نمونه](https://github.com/adivery/adivery-android-sample/blob/master/app/src/main/java/com/adivery/sample/SampleApplication.kt)، [پلاگین v2 گودو](https://docs.godotengine.org/en/stable/tutorials/platform/android/android_plugin.html). مسیر `kotlinsamples` نوشته‌شده در پرامپت مستند، در دریافت روز بررسی۴۰۴ بود؛ مسیر فعلی مخزن `kotlin` است.

## نگاشت به Adapter موجود

این جدول روش پیاده‌سازی قرارداد موجود است و قرارداد تازه‌ای برای هینت ایجاد نمی‌کند:

| callback یا وضعیت بومی | تحویل به Adapter |
| --- | --- |
| `onRewardedAdLoaded` | فقط به‌روزرسانی آمادگی؛ بدون پاداش یا نمایش خودکار |
| `onRewardedAdShown` برای نوبت معتبر | `opened` با شناسهٔ درخواست و مرحلهٔ اصلی |
| `onRewardedAdClicked` | رویداد تشخیصی؛ بدون پاداش |
| `onRewardedAdClosed(..., true)` | ابتدا `rewarded` و سپس `closed` برای همان نوبت، با حفظ ترتیب |
| `onRewardedAdClosed(..., false)` | فقط `closed` |
| `onError` شبکه | لاگ؛ بدون تبدیل مستقیم به رویداد پایان |
| نبود singleton/تنظیم معتبر/تبلیغ آماده | `unavailable` |
| خطای قطعی اجرای پل یا عدم شروع تا مهلت قرارداد | `failed` یا `unavailable`، بدون پاداش |

نکات حل‌شدنی پیش از پذیرش:

- callbackهای ادیوری `placementId` دارند، نه `request_id` بازی. پل باید یک نوبت نمایش بومی با شناسهٔ مستقل و snapshot درخواست/مرحله/اجرا نگه دارد؛ callback قدیمی نباید شناسهٔ درخواست تازه را از متغیر جاری بردارد. درخواست‌های هم‌زمان و callbackهای تکراری با این مالکیت مهار شوند.
- `poll` فعلی بعد از۳۰ثانیه بدون `opened` درخواست را آزاد می‌کند. پل نیز باید انقضای همان نوبت را بداند و کار صف‌شده برای show را پیش از اجرا دوباره اعتبارسنجی کند. اگر نمایش واقعاً شروع شده یا وضعیت بومی نامعلوم است، نمایش دوم تا تعیین تکلیف نوبت اول آغاز نشود؛ صرف پاک شدن `active` مجوز نمایش بومی دوم نیست. پاسخ‌های placement مشترک پس از timeout نباید به نوبت تازه نسبت داده شوند.
- Controller فعلی پاداش بدون `opened` را رد می‌کند. ترتیب واقعی Shown/Closed با SDK۴.۹.۰ روی دستگاه بررسی شود؛ در نبود شاهد نمایش معتبر، `opened` ساختگی برای باز کردن هینت تولید نشود. هر نیاز به تغییر رفتار فقط در مرجع قرارداد و با شواهد ثبت شود.
- Listener بومی با Retry یا حذف Controller از بین نرود؛ مسیر تحویل/ذخیرهٔ پاداش معتبر برای مرحلهٔ اصلی و قطع دسترسی به UI آزادشده طراحی شود. رفتار خروج/تعویض مرحله و درخواست برگشتی `false` از Adapter نیز بررسی شود تا دکمه معلق نماند.
- توقف تبلیغ و پس‌زمینه از مسیرهای موجود Controller اعمال شوند؛ بازگشت Activity به‌تنهایی علت توقف تبلیغ را پاک نکند. بازسازی Activity موجب initialize/ثبت listener یا اعطای دوباره نشود.
- با مرگ فرایند پیش از callback یا ذخیره، بازی محلی تضمین بازیابی پاداش تأییدنشده ندارد؛ این محدودیت SDK سمت کاربر در پذیرش ثبت شود، نه اینکه پاداش فرضی داده شود.

## انتشار و سرویس‌های اختیاری

طبق [حریم خصوصی ادیوری](https://docs.adivery.com/privacy-policy) با تاریخ اجرای 2026-07-14 برای۴.۹.x، داده‌های شناسهٔ دستگاه، موقعیت تقریبی مبتنی بر IP، تعامل تبلیغ، برنامه‌های نصب‌شده در حدود visibility، crash و diagnostics مطرح‌اند؛ AD_ID از manifest SDK ادغام می‌شود. موقعیت دقیق مشروط به مجوز موجود میزبان است. متن حریم خصوصی بازی و در صورت انتشار در Google Play، Data safety باید با نسخه و شبکه‌های واقعاً بسته‌بندی‌شده تکمیل شود؛ وضعیت فعلی بازی آفلاین برای این افشا کافی نیست. سیاست شبکه‌های mediation نیز جدا بررسی شود.

همین منبع اعلام می‌کند SDK فعلاً برای Google Play Families خودگواهی ندارد و تنظیم child-directed ارائه نمی‌کند؛ استفاده برای برنامهٔ مخصوص کودکان/عضو Families را منع می‌کند و برای مخاطب مختلط تماس با پشتیبانی می‌خواهد. این موضوع ورودی واقعی تصمیم انتشار است؛ گروه سنی پروژه هنوز در این بررسی تأیید نشده است.

[تأیید پاداش سرور](https://docs.adivery.com/server) اختیاری است: با `setUserId` و endpoint پنل، callback شامل `uid / pid / eid` می‌آید و `eid` برای جلوگیری از پاداش تکراری است. بازی فعلی حساب/سرور پاداش ندارد؛ برای هینت محلی به این مسیر نیاز نداریم. اگر بعداً لازم شد، اعتبارسنجی اصالت درخواست و سیاست retry/حذف داده باید با ادیوری روشن شوند؛ صفحهٔ فعلی جزئیات امضای callback را تعیین نمی‌کند.

[API مستقیم](https://docs.adivery.com/api) به تأیید پشتیبانی و نمایش HTML/WebView نیاز دارد؛ میان‌بر حذف پل Android محسوب نمی‌شود. کتابخانهٔ Events، ریتارگتینگ محصول و ساخت Playable برای هدف فعلی لازم نیستند. افزودن شبکهٔ اختیاری یا قالب تازه، دامنه و پذیرش مستقل دارد.

## ترتیب کار و پذیرش

جدول زیر ترتیب پذیرش است: کد ردیف‌های۲/۳ آماده و شواهد ساخت AAR ثبت شده؛ ردیف۱ از نظر شناسه‌ها/پکیج/تست پنل تکمیل و از نظر مخاطب/مارکت باز است. آزمون‌ها و پذیرش ردیف‌های۴تا۶ انجام نشده‌اند. اجرای آزمون، APK، نصب و بررسی تصویری تابع [مجوزهای پروژه](project-rules.md#tests) است.

| ترتیب | خروجی قابل بررسی | شاهد پذیرش لازم |
| --- | --- | --- |
| ۱ | شناسه‌ها، پکیج نهایی، گروه سنی/مارکت و تنظیم تست | تنظیمات ثبت‌شدهٔ پنل و تعیین امکان انتشار |
| ۲ | پل v2، Export Plugin و Gradle هم‌نسخه | بازبینی lifecycle/manifest و نسخه‌های دقیق وابستگی؛ سپس ساخت مجاز |
| ۳ | اتصال Adapter و مدیریت نوبت بومی | بازبینی ترتیب رویدادها، انقضا، listener و fallback دسکتاپ/نبود پل |
| ۴ | آزمون منطق اتصال | گسترش هدفمند `tests/test_progress_hints.gd` برای خطای یک شبکه همراه Loaded، نگاشت close(true/false)، callback قدیمی پس از timeout، درخواست هم‌زمان، رد درخواست، Retry و خطای ذخیره؛ ساخت harness اختصاصی پل در صورت نیاز |
| ۵ | آزمون Android با زوج تست | نمایش کامل و بستن زودهنگام، قطع/وصل اینترنت، نبود تبلیغ، بارگیری خودکار بعدی، Home/بازگشت، Activity recreation، مرگ فرایند، لمس و ادامهٔ صحیح ساعت؛ لاگ نوبت‌ها و نسخه/دستگاه ثبت شود |
| ۶ | پذیرش انتشار | شناسهٔ واقعی با تست پنل، manifest/مجوزهای نهایی و release با shrinker، حریم خصوصی، سپس عرضه و خاموش کردن تست پنل؛ تأیید نمایش واقعی و پاداش با شواهد |

در Android، `Adivery.setLoggingEnabled(true)` فقط برای تشخیص توسعه فعال است؛ لاگ انتشار خاموش است. آزمون‌های مرتبط و وضعیت اجرای واقعی در بخش وضعیت فعلی بالا ثبت شده‌اند؛ هیچ آزمون، APK یا نصب در این تغییر انجام نشده است.
