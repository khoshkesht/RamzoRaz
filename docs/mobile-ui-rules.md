# قواعد الزامی طراحی و چیدمان موبایل در Godot

**دامنه:** همهٔ Sceneهای فعلی و آینده، رابط‌ها، HUD، منوها، Popupها، Overlayها، پنل‌های هینت/نتیجه/شکست و چیدمان مرحله‌های این پروژه. ارجاع الزام‌آور این سند در [AGENTS.md](../AGENTS.md) ثبت شده است. این سند مرجع قواعد چیدمان است و با [قرارداد موتور](engine-contract.md) اجرا می‌شود.

ابزار، مجوز اجرای آزمون و گزارش شواهد از [قواعد پروژه](project-rules.md) خوانده شوند. ماتریس و چک‌لیست این سند معیار پذیرش‌اند؛ اجرای آن‌ها تابع [سیاست آزمون](project-rules.md#tests) است. تم و انتخاب دارایی هم در همان مرجع نگهداری می‌شود.

هدف، یکسان ماندن منطق چیدمان و قابلیت استفاده روی گوشی/تبلت است؛ نمایش درست در ادیتور به‌تنهایی معیار پذیرش نیست.

## ۱. رزولوشن مرجع اجباری

```text
Design Width: 1920
Design Height: 1080
Aspect Ratio: 16:9
Orientation: Landscape
```

تمام UIها بر اساس این رزولوشن طراحی شوند، **اما نباید به مختصات ثابت این رزولوشن وابسته باشند**. رزولوشن مرجع، اندازهٔ فیزیکی گوشی نیست؛ اندازه و Position واقعی صفحه از Viewport و Parent جاری گرفته شود.

مقادیر مشترک رزولوشن و Theme در یک محل نگهداری شوند. رزولوشن مرجع تازه‌ای داخل Scene یا اسکریپت تعریف نشود.

## ۲. سیاست Stretch پروژه

```text
Stretch Mode: canvas_items
Stretch Aspect: keep
Root UI Scale: (1, 1)
```

برای نسخهٔ فعلی، قاب معما و محتوای ضروری در محدودهٔ ۱۶:۹ حفظ می‌شوند. وجود حاشیه در نسبت‌های دیگر مجاز است؛ حذف حاشیه با کشیدن غیرهمسان یا برش سرنخ‌ها مجاز نیست. `expand` پیش‌فرض عمومی محسوب نمی‌شود؛ تغییر آن، تغییر قرارداد چیدمان است و باید همراه با بازطراحی محدودهٔ معما و آزمون‌های مرتبط انجام شود.

Stretch پروژه تنها مسیر عمومی مقیاس‌دهی است. روی ریشهٔ HUD/Overlay ضریب `screen_size / design_size` دوباره اعمال نشود. World، تصویر پس‌زمینه و HUD می‌توانند رفتار Fit متفاوت داشته باشند، اما CanvasLayer به‌تنهایی Stretch عمومی Viewport را حذف نمی‌کند. جداسازی HUD از حرکت دوربین به معنای مجاز بودن Scale دوباره نیست. [مستندات Stretch](https://docs.godotengine.org/en/4.5/tutorials/rendering/multiple_resolutions.html)، [CanvasLayer](https://docs.godotengine.org/en/4.5/classes/class_canvaslayer.html)

## ۳. تفکیک UI و صحنهٔ معما

- HUD، Menu، Dialog، Popup، پنل نتیجه و سایر رابط‌های صفحه با `Control` ساخته شوند.
- اشیای قابل تعامل معما می‌توانند طبق قرارداد موتور `Node2D` باشند. موقعیت ثابت آن‌ها در فضای طراحی مرحله مجاز است؛ این مجوز شامل HUD نیست.
- HUD و Overlay در CanvasLayer مستقل از World قرار بگیرند و برای دنبال کردن دوربین تنظیم نشوند. Layerهای متفاوت و مشخص برای ترتیب نمایش استفاده شود.
- Sceneهای جدید همان ریشه و اجزای مشترک UI را استفاده کنند؛ هر مرحله سیستم Scale یا Safe Area تازه‌ای نسازد.

ساختار پایه:

```text
Main
├── PuzzleStage (Node2D؛ فضای مرجع مرحله)
├── HUDLayer (CanvasLayer؛ layer = 10)
│   └── HUDRoot (Control؛ Full Rect، LTR)
│       └── SafeRoot (Control؛ محدودهٔ امن محاسبه‌شده)
│           └── Padding (MarginContainer؛ Full Rect)
│               └── HUDContent (Container)
└── OverlayLayer (CanvasLayer؛ layer = 20)
    └── OverlayRoot (Control؛ Full Rect، LTR)
        ├── Dimmer (ColorRect؛ Full Rect)
        └── SafeRoot (Control؛ محدودهٔ امن محاسبه‌شده)
            └── DialogLayout (Container)
```

### ۳.۱. رزرو ۱۰٪ بالای قاب برای HUD

**قاعدهٔ طراحی مرحله:** ۱۰٪ ارتفاع از بالای قاب محتوای بازی برای منو، امتیاز، زمان و سایر اجزای نوار بالایی HUD در نظر گرفته شود. اشیای نیازمند جابه‌جایی یا اکشن، مقصدهای Drop، سرنخ‌ها و هر عنصر مؤثر در حل معما در این ناحیه قرار نگیرند؛ چیدمان آن‌ها در بخش پایین‌تر قاب انجام شود.

- مبنای درصد، ارتفاع قاب محتوای بازی پس از اعمال `canvas_items / keep` است؛ حاشیه‌های بیرون قاب جزو آن نیستند. در فضای مرجع ۱۹۲۰×۱۰۸۰، نوار بالا از `y=0` تا `y=108` است؛ ۱۰۸ فقط مقدار متناظر در دادهٔ مرجع است و نباید به ارتفاع ثابت HUD روی نمایشگر تبدیل شود.
- نوار HUD با Anchor/Container و اندازهٔ جاری Parent تعیین شود؛ کنترل‌های آن در تقاطع نوار با Safe Area و با Padding مناسب قرار بگیرند. Safe Area همچنان طبق بخش۱۰ محاسبه شود؛ رزرو۱۰٪ جای آن را نمی‌گیرد.
- کل محدودهٔ دیداری و لمس عنصر مهم، با احتساب اندازه، Scale و چرخش، پایین نوار باشد؛ پایین‌بودن مرکز شیء به‌تنهایی کافی نیست. مقصدها، محدودهٔ Drag و مسیر اکشن/انیمیشن نیز طوری طراحی شوند که اشیای معما زیر نوار HUD نروند.
- پس‌زمینه و تزئینات فاقد سرنخ می‌توانند پشت نوار ادامه داشته باشند. اگر سؤال، متن بلند یا چیدمان واقعی HUD پایین‌تر از۱۰٪ امتداد داشت، محدودهٔ واقعی اشغال‌شدهٔ آن هم در جای‌گذاری اشیای مؤثر و مسیرهای تعامل لحاظ شود.
- هنگام Resize، حدود نوار و محدودهٔ اشغال HUD با همان تبدیل مشترک نمایش/لمس دوباره محاسبه شوند. بررسی عددی هم‌پوشانی در ماتریس اندازه‌ها انجام شود؛ بررسی تصویری فقط با درخواست صریح کاربر مجاز است.

## ۴. ریشهٔ UI و Parent

ریشه‌های HUD/Overlay باید Full Rect با Anchorهای `left/top=0` و `right/bottom=1` و **هر چهار Offset برابر صفر** باشند. ابعاد ثابت ۱۹۲۰×۱۰۸۰ به ریشه تحمیل نشود؛ Root محدودهٔ Viewport یا Parent معتبر را دنبال می‌کند.

پیش از چیدن فرزند، Parent و زنجیرهٔ تبدیل‌های آن بررسی شوند. Full Rect زیر Parent با اندازهٔ صفر یا نامناسب، مشکل را حل نمی‌کند. SafeRoot استثنای آگاهانهٔ ریشه است: Rect آن از Safe Area محاسبه می‌شود و صرفاً Full Rect کل صفحه نیست. Dialog نیز فرزند داخل این محدوده است و لازم نیست تمام صفحه را پر کند.

## ۵. ممنوعیت وابستگی UI به مختصات صفحه

این روش برای جای HUD مجاز نیست:

```gdscript
menu_button.position = Vector2(1840, 24)
```

موقعیت از Parent، لبه، مرکز یا Container تعیین شود. اعداد ثابت برای Padding، فاصله، ابعاد آیکون، ضخامت و حداقل اندازه مجازند؛ واحد آن‌ها **واحد منطقی طراحی** است، نه الزاماً پیکسل فیزیکی دستگاه.

حرکت نمایشی UI مثل انیمیشن باز شدن پنل می‌تواند Position/Offset را در یک محدودهٔ محلی کنترل کند؛ مقصد نهایی باید از چیدمان جاری به دست آید. انیمیشن مجوز استفاده از مختصات ثابت صفحه نیست.

## ۶. Anchorها باید کامل تعریف شوند

در عناصر خارج از Container، هر دو Anchor افقی و هر دو عمودی، چهار Offset و جهت Grow باید متناسب با محل عنصر تعیین شوند. تنظیم فقط `anchor_right=1` برای دکمهٔ بالا راست کافی نیست.

مثال زیر برای فرزند مستقیم SafeRoot با جهت چیدمان LTR است؛ ابعاد و Margin فقط نمونه‌اند:

```text
Top-right button:
anchor_left = 1
anchor_right = 1
anchor_top = 0
anchor_bottom = 0
offset_left = -112
offset_right = -32
offset_top = 24
offset_bottom = 104
grow_horizontal = Begin
grow_vertical = End
```

چپ/راست فیزیکیِ هر جزء در طراحی همان Scene مشخص شود؛ موقعیت Menu، Hint یا Avatar قانون یکسان برای همهٔ بازی‌ها ندارد. Dialog نسبت به محدودهٔ امن مرکز شود. [مستندات Anchor](https://docs.godotengine.org/en/4.5/tutorials/ui/size_and_anchors.html)

## ۷. مالک چیدمان هر عنصر فقط یکی باشد

برای چیدمان گروهی از MarginContainer، HBoxContainer، VBoxContainer، CenterContainer، PanelContainer، GridContainer یا AspectRatioContainer مناسب استفاده شود.

Position، Size، Anchor یا Offset **فرزند مستقیم Container** با اسکریپت برای چیدمان تغییر نکند. اندازه از Size Flags، حداقل اندازه و تنظیم خود Container تعیین شود. برای انیمیشن، یک Wrapper تحت مدیریت Container و عنصر نمایشی درون آن استفاده شود تا Container و اسکریپت مالک یک Rect نباشند. [مستندات Container](https://docs.godotengine.org/en/4.5/tutorials/ui/gui_containers.html)

## ۸. Size Flags، حداقل اندازه و کمبود فضا

- Fill، Expand، Shrink Center و Stretch Ratio مطابق نقش عنصر تعیین شوند؛ Spacer خالی می‌تواند Expand بگیرد.
- Expand فضای اضافه را تقسیم می‌کند؛ راه‌حل خودکار برای محتوای بزرگ‌تر از Parent نیست.
- Minimum Size، اندازهٔ فونت و حداقل اندازهٔ Texture باید بررسی شوند تا Parent را ناخواسته بزرگ نکنند.
- سؤال/هینت باید شکست خط و رفتار مشخص هنگام متن بلند داشته باشند. محتوای بلند می‌تواند در ScrollContainer باشد؛ عنوان و دکمه‌های ضروری در محدودهٔ امن باقی بمانند.
- ابعاد Dialog به اندازهٔ امن جاری محدود شود؛ حداقل یا حداکثر ثابت نباید باعث بیرون‌زدگی روی صفحهٔ کوچک شود. محدود کردن اندازه فقط در `_ready` کافی نیست؛ تغییر اندازه نیز باید رسیدگی شود.
- اگر فضا کافی نیست، چیدمان باید بازآرایی یا اسکرول شود؛ کوچک کردن کل UI تا حد ناخوانایی مجاز نیست.

## ۹. پس‌زمینهٔ تزئینی و سرنخ معما

TextureRect پس‌زمینهٔ تزئینی می‌تواند Full Rect، `expand_mode = EXPAND_IGNORE_SIZE` و `stretch_mode = STRETCH_KEEP_ASPECT_COVERED` داشته باشد. Crop آن مجاز است اگر اطلاعات ضروری حذف نشود.

تصویر دارای سرنخ، اشیای معما یا ناحیهٔ Drop با این سیاست برش داده نشود؛ تصویر و منطق تعامل باید در یک فضای تبدیل‌شدهٔ مشترک بمانند. اندازهٔ Texture نباید به‌صورت ناخواسته Minimum Size کل HUD را تعیین کند. [مستندات TextureRect](https://docs.godotengine.org/en/4.5/classes/class_texturerect.html)

## ۱۰. Safe Area واقعی و Padding

Safe Area واقعی Android از `DisplayServer.get_display_safe_area()` خوانده شود. خروجی در فضای نمایشگر است؛ نباید مستقیماً به Offset یا Margin منطقی HUD داده شود. محدوده با ناحیهٔ رندر بازی تقاطع داده، با در نظر گرفتن Scale، موقعیت Viewport و حاشیه‌های `keep` به فضای UI تبدیل و سپس Padding اضافه شود. هر سطح باید Inset خودش را فقط یک بار اعمال کند. [مستندات Safe Area](https://docs.godotengine.org/en/4.5/classes/class_displayserver.html#class-displayserver-method-get-display-safe-area)

Margin ثابت جای Safe Area واقعی را نمی‌گیرد. اگر اطلاعات دستگاه معتبر نیست، محدودهٔ Viewport با Padding پیش‌فرض استفاده و نیاز به آزمون دستگاه ثبت شود. تغییر اندازهٔ Viewport، تغییر محدودهٔ امن و بازگشت از پس‌زمینه باید محاسبه را تازه کنند.

HUD و دکمه‌های مهم داخل ناحیهٔ امن باشند؛ Dimmer و پس‌زمینه می‌توانند کل ناحیهٔ رندر را بپوشانند. استفاده از عرض فیزیکی صفحه به‌جای عرض Parent یا Viewport برای چیدمان UI مجاز نیست.

## ۱۱. RTL متن از چیدمان فیزیکی جدا باشد

ریشه‌های HUD و Overlay صریحاً `LAYOUT_DIRECTION_LTR` باشند تا چیدمان فیزیکی به زبان سیستم وابسته نشود. متن سؤال، هینت و Label فارسی `TEXT_DIRECTION_RTL` داشته باشد؛ زمان و نمایش عددی ساخت‌یافته مثل `03:20` جهت متن LTR داشته باشند. Alignment متن جدا از جهت متن تنظیم شود.

```gdscript
hud_root.layout_direction = Control.LAYOUT_DIRECTION_LTR
overlay_root.layout_direction = Control.LAYOUT_DIRECTION_LTR
question_label.text_direction = Control.TEXT_DIRECTION_RTL
hint_label.text_direction = Control.TEXT_DIRECTION_RTL
timer_label.text_direction = Control.TEXT_DIRECTION_LTR
```

RTL کردن `layout_direction` برای فارسی کردن متن ممنوع است؛ در Godot این ویژگی Anchorها، Marginها و ترتیب افقی Containerها را هم آینه می‌کند. متن فارسی/عدد/نشانهٔ ترکیبی باید در خروجی نیز بررسی شود. [مستندات BiDi و آینه‌سازی UI](https://docs.godotengine.org/en/4.5/tutorials/i18n/internationalizing_games.html#bidirectional-text-and-ui-mirroring)

## ۱۲. فونت و اندازهٔ قابل استفاده

فونت فارسی و Theme مشترک همراه خروجی بسته‌بندی شوند؛ نمایش متن به فونت نصب‌شده روی گوشی وابسته نباشد. اندازهٔ متن و سطح لمس بر مبنای طراحی مرجع تعیین و در کوچک‌ترین اندازهٔ آزمون روی دستگاه بررسی شوند؛ بزرگ بودن رزولوشن فایل یا اسکرین‌شات، خوانایی و قابلیت لمس را ثابت نمی‌کند.

پنل‌ها، متن‌ها و دکمه‌ها نباید فقط با Scale ریشه بزرگ/کوچک شوند. تغییر اندازهٔ ضروری از Theme، چیدمان و اندازهٔ محتوا مدیریت شود. تفاوت فونت، متن طولانی و حداقل اندازه هنگام بررسی UI لحاظ شوند.

## ۱۳. Popup، Overlay و ورودی

Popup و Dialog متعلق به World یا دوربین نیستند؛ در OverlayLayer و نسبت به SafeRoot چیده شوند. Panel مرکزی از Container یا Anchor مرکزی کامل استفاده کند. اندازهٔ پنل پس از تغییر Viewport دوباره با فضای امن سازگار شود.

Controlهای تزئینی ورودی را نبلعند؛ دکمه و Modal مطابق [قرارداد ورودی موتور](engine-contract.md) ورودی را مصرف کنند. یک لمس نباید هم‌زمان دکمهٔ Overlay و شیء معما را فعال کند. Overlay غیرفعال نباید ورودی بازی را مسدود کند.

## ۱۴. یک مسیر تبدیل برای نمایش و لمس

مختصات نمایشگر، Viewport، Parent و صحنهٔ معما یکسان فرض نشوند. تبدیل ورودی دقیقاً یک بار از مسیر معتبر انجام شود. Hit Test، Drag و Drop باید با همان موقعیت/Scale/چرخشِ نمایش‌داده‌شده کار کنند؛ تغییر رزولوشن نباید محل لمس را از تصویر جدا کند.

برای اطلاعات چیدمان ابتدا Rect جاری Viewport/Parent گرفته شود؛ اگر اندازه هنوز آماده نیست، محاسبه تا آماده شدن چیدمان به تعویق بیفتد. برای تغییرات بعدی به resized/size_changed مرتبط واکنش داده شود؛ Rect اندازه‌گیری‌شده در اولین فریم برای همیشه cache نشود.

## ۱۵. ماتریس آزمون اجباری

هر ساخت یا اصلاح چیدمان UI در این اندازه‌ها بررسی شود:

| اندازه | هدف |
| --- | --- |
| 1920×1080 | مرجع ۱۶:۹ |
| 2400×1080 | گوشی ۲۰:۹ |
| 2280×1080 | گوشی ۱۹:۹ |
| 2340×1080 | گوشی ۱۹٫۵:۹ |
| 1920×1200 | تبلت ۱۶:۱۰ |
| 2048×1536 | تبلت ۴:۳ |
| 1280×720 و 960×540 | خوانایی و کمبود فضای نمایش |

آزمون در پنجرهٔ بازی با ابعاد واقعاً متفاوت انجام شود؛ زوم پیش‌نمایش ادیتور، آزمون نسبت تصویر نیست. اندازهٔ Viewport منطقی و ناحیهٔ رندر واقعی در Debug ثبت شوند. تمام حالت‌های UI مربوط به تغییر، شامل متن طولانی و پنل‌های باز، بررسی شوند.

خروجی APK روی گوشی واقعی نیز برای Safe Area، لمس، فونت، نوارهای سیستم و بازگشت از پس‌زمینه بررسی شود. اگر ابزار یا دستگاه موجود نیست، آزمون‌های قابل انجام اجرا و موارد آزموده‌نشده صریح گزارش شوند؛ ادعای تأیید موبایل بدون اجرای واقعی مجاز نیست.

## ۱۶. معیار پذیرش هر تغییر چیدمان

- عناصر ضروری و دکمه‌ها داخل محدودهٔ امن و قابل مشاهده/لمس باشند.
- نوار۱۰٪ بالای قاب برای HUD رزرو باشد؛ محدودهٔ دیداری/لمس، مقصد Drop و مسیر حرکت اشیای مؤثر در معما با این نوار یا سایر بخش‌های اشغال‌شدهٔ HUD هم‌پوشانی نداشته باشند.
- سؤال، هینت، زمان و نتیجهٔ مهم Clip نشوند؛ محتوای ScrollContainer استثنای مدیریت‌شده است.
- ترتیب فیزیکی چپ/راست و محل مرکز با تغییر زبان سیستم یا اندازهٔ صفحه عوض نشود.
- ریشه Full Rect با Offset صفر باشد؛ SafeRoot از محدودهٔ واقعی ساخته شود.
- Container و اسکریپت هم‌زمان جای یک عنصر را مدیریت نکنند.
- UI دوبار Scale نشود؛ حداقل اندازه یا تصویر، Parent را ناخواسته بزرگ نکند.
- پس‌زمینه نسبت تصویر را حفظ کند و هیچ سرنخ معما Crop نشود.
- محدودهٔ لمس با تصویر تطبیق داشته باشد؛ لمس UI روی معما اثر نگذارد.
- تغییر اندازه/بازگشت از پس‌زمینه موجب مختصات یا Safe Area کهنه نشود.
- نتایج ماتریس آزمون و محدودیت آزمون دستگاه در گزارش تغییر ثبت شوند.

تأیید بصری صرف در رزولوشن مرجع کافی نیست. هر خروج عمدی از Parent، مانند Scroll یا افکت تزئینی، باید مدیریت‌شده باشد؛ این استثنا مجوز بیرون رفتن دکمه و محتوای ضروری نیست.

## ۱۷. اصلاح چیدمان قدیمی

هنگام تغییر UI موجود، `position`، `global_position`، `set_position`، Scale، Offsetهای ثابت و اسکریپت‌های Resize بررسی شوند. این موارد در گیم‌پلی یا انیمیشن محلی لزوماً اشکال نیستند؛ استفادهٔ آن‌ها برای وابسته کردن HUD به رزولوشن ثابت باید با Anchor/Container یا اندازه‌گیری Parent جایگزین شود.

تغییر مرتبط باید مشکل مالکیت چیدمان، Parent نامناسب، Scale دوباره یا RTL ناخواسته را اصلاح کند؛ افزودن Offset جبرانی وابسته به مدل گوشی مجاز نیست. قواعد مشترک در یک جزء مشترک اجرا شوند تا Sceneهای بعدی همان رفتار را داشته باشند.

## ۱۸. ترتیب الزامی کار

1. تعیین کن عنصر UI است یا شیء گیم‌پلی و فضای مختصات آن چیست.
2. Parent، Layer، سیاست Stretch و مالک Rect را مشخص کن.
3. Root، SafeRoot، Anchor یا Container مناسب را تنظیم کن.
4. اندازهٔ محتوا، Theme، Margin، Size Flags و حداقل اندازه را تعیین کن.
5. جهت چیدمان فیزیکی و جهت متن را جدا تنظیم کن.
6. نمایش و ورودی را با یک مسیر تبدیل هماهنگ کن.
7. Resize، Safe Area و حالت‌های باز شدن پنل را بررسی کن.
8. ماتریس آزمون و معیارهای پذیرش را اجرا و نتیجهٔ واقعی را گزارش کن.
